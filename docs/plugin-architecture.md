# Dashboard Plugin Architecture

Plugin system architecture: workspace build-time + external runtime loading + server discovery.

## Three Plugin Sources

Dashboard discovers plugins from three sources in order (earlier sources shadow later):

| Source | Location | Type | Loading |
|--------|----------|------|---------|
| Workspace | `packages/*/package.json` | Vite-compiled at build time | Static imports in `plugin-registry.tsx` |
| Pi-installed | `~/.pi/agent/settings.json#packages[]` | Vite-compiled at build time | Static imports + server discovery |
| Dashboard-installed | `~/.pi/dashboard/plugins/<id>/` | MF remotes pre-built by plugin author | Runtime dynamic import + MF |

Workspace plugins (build-time) coexist with dashboard-installed plugins (runtime). No rebuild needed for external plugins.

## Slot Taxonomy

Thirteen slot ids, some react-only, some tool-renderer-specific:

- `sidebar-folder-section` — React component, sidebar left pane workspace folder sections
- `session-card-badge` — React component, session card top-left badge area (e.g., "SSH")
- `session-card-action-bar` — React component, session card action button row
- `session-card-memory` — React component, session card memory gauge (replaces or augments built-in)
- `session-card-flows` — React component, session card flow list area
- `workspace-action-bar` — React component, workspace toolbar action buttons
- `content-view` — React component, main content pane (full-screen or modal)
- `content-header-sticky` — React component, sticky header above content
- `content-inline-footer` — React component, inline footer in content pane
- `anchored-popover` — React component, floating popover anchored to session
- `command-route` — React component, command route handler (e.g., `/cmd:myplugin/action`)
- `settings-section` — React component, settings page section
- `tool-renderer` — React component, tool renderer (e.g., bash, python, sql)
- `shell-overlay-route` — React component, shell overlay route (Electron only)

## Slot Registry & Reactivity

`SlotRegistry` (client) tracks all claims per slot. Clients subscribe via `registry.subscribe(slotId, fn)` to receive live claim list.

Each claim wraps a resolved React component:

```typescript
interface RuntimePluginClaim {
  slot: string;
  component?: React.ComponentType<any>;
  toolName?: string;
  [key: string]: unknown;
}
```

On plugin load, claims added to registry → subscribers notified → UI re-renders. On plugin unload, claims removed → subscribers notified.

## Workspace Plugins (Build-Time)

Vite plugin scans `packages/*/package.json` for `pi-dashboard-plugin` field without `mfRemote`. Generates `src/client/generated/plugin-registry.tsx` with static imports:

```typescript
// Generated by Vite plugin
import Badge from '@blackbelt-technology/my-plugin/src/slots/Badge';
import type { PluginClaim } from '@blackbelt-technology/dashboard-plugin-runtime';

export const PLUGIN_CLAIMS: PluginClaim[] = [
  { slot: 'session-card-badge', component: Badge, priority: 100 }
];
```

Included in initial bundle. No runtime loading. Requires rebuild to add/update.

## External Plugins (Runtime Loading)

Dashboard plugins published to npm with `mfRemote` in manifest. Installed via Plugins UI into `~/.pi/dashboard/plugins/<id>/`. Loaded dynamically at runtime without rebuild.

### Module Federation Topology

- **Host**: dashboard (Rspack build with `ModuleFederationPlugin`)
- **Remote**: plugin (standalone Rspack build with MF remote entry)
- **Shared singletons**: react, react-dom, @blackbelt-technology/dashboard-plugin-runtime
- **Transport**: HTTP `GET /plugins/<id>/dist/remoteEntry.js`

Host declares shared deps with `singleton: true, requiredVersion: '^19.0.0'`. Remote negotiates same at load time. If version mismatch, fallback to remote's version (single React tree preserved).

### Runtime Loading Flow

```
User installs plugin via Plugins UI
  → POST /api/plugins/install { source: "npm:@scope/my-plugin" }
  → Server downloads npm tarball, extracts to ~/.pi/dashboard/plugins/<id>/
  → discoverPlugins() rescans, finds new dashboard-installed plugin
  → broadcasts plugins_changed WS event with new plugin metadata
  ↓
Client receives plugins_changed
  → handlePluginsChanged(plugins) diffs loaded vs. discovered
  → loadRemotePlugin(plugin) for newly enabled plugins
    1. Preflight HEAD /plugins/<id>/dist/remoteEntry.js (404 = error)
    2. Dynamic import("/plugins/<id>/dist/remoteEntry.js") loads MF remote
    3. Call remote.init(api) where api = createDashboardPluginApi(pluginId)
    4. Track cleanup functions: claims, subscriptions, listeners
  → Browser renders claim components via SlotRegistry subscriptions
  ↓
On plugin unload/disable
  → Call init() cleanup function (all unregisters run)
  → Remove all claims from SlotRegistry
  → Unsubscribe all onEvent + subscribeSession listeners
  → Remote module garbage-collected
```

Duration: ~2s from `plugins_changed` broadcast to first claim visible.

### Error Handling

- Preflight 404 → logged, plugin marked error, `plugin-load-error` event dispatched
- import() throws (bad JS, network) → logged, plugin marked error, event dispatched
- init() throws (runtime error in plugin code) → logged, plugin marked error, event dispatched
- Claim component throws (render error) → per-claim `SlotErrorBoundary` catches, logs, renders error pill in dev, event dispatched

PluginStatusStore observes `plugin-load-error` events, updates UI in Plugins section.

## Server Discovery & Plugin Bundle Serving

### Discovery

`discoverPlugins()` scans three sources, returns merged list of `PluginStatus`:

```typescript
interface PluginStatus {
  id: string;
  displayName: string;
  source: 'workspace' | 'global' | 'dashboard-installed';
  enabled: boolean;
  manifest: PluginManifest;
  mfRemote?: string;
  error?: string;
}
```

Dashboard-installed plugins read from manifest file `~/.pi/dashboard/plugins/<id>/dashboard-plugin.json`.

### Bundle Serving

Route `GET /plugins/:id/*` serves files from `~/.pi/dashboard/plugins/<id>/`. Gated by `localhostGuard` (localhost + 127.0.0.1 only).

```
GET /plugins/my-plugin/dist/remoteEntry.js
  → reads ~/.pi/dashboard/plugins/my-plugin/dist/remoteEntry.js
  → sets Content-Type: application/javascript
  → returns file
```

Plugin authors pre-build to `dist/`. Rspack with MF remote entry outputs `dist/remoteEntry.js` + `dist/main.*.js` + `dist/*.css`.

### Dev Override

`PI_DASHBOARD_PLUGIN_DEV` env var (JSON map) proxies plugin requests to dev server:

```bash
PI_DASHBOARD_PLUGIN_DEV='{"my-plugin":"http://localhost:3456"}' npm run dev
```

`GET /plugins/my-plugin/dist/remoteEntry.js` → proxied to `http://localhost:3456/dist/remoteEntry.js`. Enables live editing + HMR in plugin dev server.

### Installation Routes

- `POST /api/plugins/install { source: "npm:<pkg>" }` — downloads tarball from npm, extracts to `~/.pi/dashboard/plugins/<id>/`, broadcasts `plugins_changed`
- `POST /api/plugins/uninstall/:id` — removes plugin directory, broadcasts `plugins_changed`
- `GET /api/plugins/available?q=<search>` — searches npm for packages with keyword `pi-dashboard-plugin`

## Client-Side Plugin Loader

`plugin-loader.ts` manages lifecycle:

### Initialization

On app mount:
1. Fetch `GET /api/plugins` (initial list)
2. `wirePluginLoader({ registry, send })` (dependencies)
3. `handlePluginsChanged(plugins)` (load all enabled plugins with `mfRemote`)

### Reactivity

On `plugins_changed` WS broadcast:
1. Diff current loaded ids vs. new discovery
2. `unloadPlugin(id)` for removed/disabled (calls cleanup)
3. `loadRemotePlugin(plugin)` for new/enabled (calls init)
4. Notify subscribers via `subscribeLoadState(fn)`

### Loaded Plugin Tracking

```typescript
interface LoadedPlugin {
  id: string;
  cleanupFns: Array<() => void>;
}

const loadedPlugins = new Map<string, LoadedPlugin>();
```

All cleanup functions (claim unregisters, event unsubscribes) stored per plugin. On unload, all run sequentially.

## DashboardPluginApi

Typed surface passed to `init(api)`:

```typescript
interface DashboardPluginApi {
  pluginId: string;                                        // read-only
  registerClaim(claim: RuntimePluginClaim): () => void;    // unregister fn
  getSession(id: string): DashboardSession | undefined;
  getAllSessions(): DashboardSession[];
  subscribeSession(fn: (sessions) => void): () => void;    // unsubscribe fn
  onEvent(type: string, fn: (event) => void): () => void;  // unsubscribe fn
  showToast(msg: string, variant?: ToastVariant): void;
  getConfig<T>(): T;
  setConfig(partial: Record<string, unknown>): Promise<void>;
}
```

Proxy initialized in `<script>` pre-React on page load. Queues calls until React mounts, then flushes. Scoped by plugin id (all operations implicitly bound to caller).

### Claim Registration

`registerClaim(claim)` adds claim to SlotRegistry. Returns unregister function. For `tool-renderer` claims, internally delegates to `registerToolRenderer(toolName, component, { headerChips?, summary? })`.

### Session Subscription

`subscribeSession(fn)` wires `SlotRegistry.subscribe('__sessions__', fn)`. Callback fired on session list change. Unsubscribe removes listener.

### Event Subscription

`onEvent(type, fn)` wires WS message type listener. Broadcast events (e.g., `session_created`, `event_forward`) invoke callback. Unsubscribe removes listener.

### Config Storage

Plugin-scoped config in-memory (backed by server persistence). `getConfig()` synchronous ({}  until first sync). `setConfig(partial)` sends `set_plugin_config` message over WS, server merges + persists. All plugins receive `plugin_config_changed` event.

## Slot Error Boundary

`SlotErrorBoundary` wraps each claim component:

```typescript
<SlotErrorBoundary pluginId={claim.pluginId} slotId={claim.slot}>
  <ClaimComponent {...props} />
</SlotErrorBoundary>
```

On component error:
- Logs to console with plugin id + slot name
- In dev: renders red error pill (`"pluginId ⊘ slotId"`)
- Dispatches `plugin-load-error` CustomEvent (PluginStatusStore observes)
- Siblings in same slot unaffected

Per-claim isolation means broken plugin components degrade gracefully — don't crash dashboard.

## Server-Side Plugin Integration

### Dynamic Server Entry Loading

`loadServerEntries()` scans manifest files for `server` field. On boot + after `plugins_changed`:

```typescript
// Plugin manifest has "server": "./src/server/index.ts"
const serverModule = await import('file:///home/user/.pi/dashboard/plugins/my-plugin/src/server/index.ts');
await serverModule.registerPluginServer(fastify);
```

Failure isolated. Broken import/export caught, logged, plugin continues. Dashboard stays online.

### Dynamic Bridge Entry Loading (Optional)

Plugins with `bridge` field export bridge handlers for pi extension integration (similar to server entry pattern).

## Lifecycle Summary

### Load
1. User installs via Plugins UI (or plugin discovered at boot)
2. `loadRemotePlugin(plugin)` called
3. Preflight + import MF remote
4. Call `init(api)` in plugin context
5. Plugin registers claims
6. Claims appear in SlotRegistry
7. Slots re-render (subscribers notified)

### Runtime
- Plugin claims rendered in slot positions
- Plugins subscribe to events + session changes
- User interacts with plugin components
- Plugins call api methods (showToast, setConfig, etc.)

### Unload
1. User disables/uninstalls plugin
2. `unloadPlugin(id)` called
3. Call `init()` cleanup function (all unregisters run)
4. Remove all claims from SlotRegistry
5. Unsubscribe all listeners
6. Remote module dereferenced, GC'd

## Shared Dependencies

Dashboard enforces singleton sharing via MF:

```typescript
// Rspack host config
new ModuleFederationPlugin({
  shared: {
    react: { singleton: true, requiredVersion: '^19.0.0' },
    'react-dom': { singleton: true, requiredVersion: '^19.0.0' },
    '@blackbelt-technology/dashboard-plugin-runtime': { singleton: true }
  }
})
```

Plugins declare same in their Rspack config. Single React tree across host + remotes. If remote has different version, warning logged, both versions coexist (MF fallback).

## Vite Plugin Behavior

Workspace plugins: `mfRemote` absent from manifest → included in static registry.
External plugins: `mfRemote` present → excluded from static registry → loaded dynamically.

Build separation:
- Vite: builds workspace + client, generates `plugin-registry.tsx`
- Rspack: builds dashboard host (Rspack build for MF)
- Rspack: (external) builds each plugin remote independently

## Summary

- Workspace plugins: build-time, static imports, coexist with external plugins
- External plugins: runtime loading, Module Federation, installed via Plugins UI
- Discovery: workspace → pi-installed → dashboard-installed (sources shadow)
- Server: handles install/uninstall, serves pre-built bundles, loads server entries
- Client: dynamic import + init contract, SlotRegistry + Slot components, per-claim error isolation
- API: typed DashboardPluginApi, claim registration, session/event subscriptions, config storage
- Lifecycle: load → init → claims rendered → unload → cleanup
